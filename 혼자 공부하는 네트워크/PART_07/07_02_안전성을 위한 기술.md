# 07_2 안전성을 위한 기술

## 1. 왜 암호화가 필요한가

- 인터넷으로 메시지를 그냥 보내면(평문) 중간에 누군가 몰래 볼 수 있음 → 도청
- 중간에서 내용을 바꿔치기할 수도 있음 → 변조
- 그래서 메시지를 남이 알아볼 수 없게 바꿔서 보내야 함

![제3자가 중간에서 “계좌번호 1234”를 “4321”로 바꿔치기하는 모습](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/b098e867-4dea-46d0-a10c-b3aa87813579.png)

### 용어

- 암호화(encryption): 원래 데이터를 알아볼 수 없는 형태로 바꾸는 것
- 복호화(decryption): 암호화된 데이터를 다시 원래대로 되돌리는 것
- 평문(원문): 암호화 전의 원래 데이터
- 암호문: 암호화된 결과 데이터

## 2. 키(key)란

- 암호화·복호화에 쓰는 비밀 값. 자물쇠의 열쇠 같은 역할
- 생김새는 의미 없어 보이는 문자열임
- 원문 + 키 → 수학 계산(암호화 알고리즘) → 암호문
- 받는 쪽은 암호문을 복호화해서 원문을 얻음
- 키가 없는 제3자는 암호문을 봐도 뜻을 모름

![원문 + 키 → 암호문 전송 → 받는 쪽에서 복호화. 중간 사람은 “뭐지?” 하는 모습](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/b29fef40-12fd-44e6-9619-d775e63a76e6.png)

암호화 방식은 크게 두 가지임

- 대칭 키 암호화
- 비대칭 키 암호화 (= 공개 키 암호화)

## 3. 대칭 키 암호화 (symmetric key cryptography)

- 잠글 때와 열 때 같은 키 하나를 씀
- 보내는 쪽, 받는 쪽이 똑같은 키를 나눠 가져야 함

![A와 B가 같은 키로 암호화·복호화를 주고받는 모습](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/2cb5642d-9cdd-4de5-8417-4314cafb12e8.png)

### 문제점: 키를 어떻게 안전하게 전달하나

- 키 하나로 다 풀리니까 키가 새면 끝임. 그동안 암호화한 게 전부 소용없어짐
- 그런데 키를 상대에게 안전하게 보낼 방법이 있다면? → 그 방법으로 그냥 메시지를 보내면 되니 암호화가 필요 없어짐
- 즉, “키를 안전하게 전달하는 문제”는 대칭 키만으로는 해결이 안 됨

![“키를 안전하게 보낼 수 있어!” / “그 방법으로 데이터를 보내면 되잖아?” 대화 장면](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/0161d8a2-d558-477e-88cd-a56e347d0103.png)

## 4. 공개 키 암호화 (public key cryptography)

- 비대칭 키 암호화라고도 부름
- 서로 다른 두 개의 키를 한 쌍으로 씀
    - 공개 키(public key): 누구에게 줘도 되는 키
    - 개인 키(private key): 나만 가지고 있어야 하는 키
- 한 키로 잠그면 반드시 다른 짝 키로만 열 수 있음
- 한쪽 키만 보고 다른 쪽 키를 알아낼 수는 없음

### 공개 키로 잠그고, 개인 키로 연다

- 공개 키는 잠그는 용도라서 남이 알아도 원문을 알 수 없음 → 막 공개해도 됨
- 개인 키만 절대 새지 않게 지키면 됨

![클라이언트가 공개 키로 암호화 → 서버가 개인 키로 복호화](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/06647a53-827c-492a-908a-fa8f0fdb84e4.png)

### 예시: A가 B에게 “안녕, 나는 A야”를 보내는 과정

1. A가 B에게 공개 키를 달라고 함
2. B가 자기 공개 키를 A에게 보냄 (공개돼도 괜찮으니 그냥 보냄)
3. A가 B의 공개 키로 메시지를 잠가서 보냄
4. 중간에 누가 봐도 암호문이라 뜻을 모름
5. B는 자기 개인 키로 열어서 원문을 확인함

반대로 B가 A에게 보낼 땐, A의 공개 키로 잠그고 A가 자기 개인 키로 엶

![A → (B의 공개 키로 암호화) → 암호문 → (B의 개인 키로 복호화) → B](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/d5359dd5-dab6-42bc-ad7f-dfd87a04156c.png)

## 5. 두 방식 비교와 함께 쓰기

| 구분 | 대칭 키 | 공개 키 |
| --- | --- | --- |
| 키 개수 | 1개 (같은 키) | 2개 (공개 키 + 개인 키) |
| 속도 | 빠름, 부담 적음 | 느림, 부담 큼 |
| 키 전달 | 안전하게 전달하기 어려움 | 안전하게 공유 가능 |

### 섞어서 쓰는 방법

- 장점만 챙기려고 둘을 같이 쓰는 경우가 많음
    1. 실제 데이터용 대칭 키를 하나 만듦
    2. 이 대칭 키를 상대의 공개 키로 잠가서 보냄 → 안전하게 전달됨
    3. 상대는 개인 키로 열어서 대칭 키를 얻음
    4. 이후 실제 데이터는 빠른 대칭 키로 주고받음
- 이렇게 쓰이는 대칭 키를 세션 키(session key)라고 부름

A의 세션 키 → 공개 키로 암호화 → 개인 키로 복호화 → B가 세션 키를 얻음

![A의 세션 키 → 공개 키로 암호화 → 개인 키로 복호화 → B가 세션 키를 얻음](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/d2a271de-c0f2-4d0f-8aec-c3a42cb693b6.png)

A의 세션 키 → 공개 키로 암호화 → 개인 키로 복호화 → B가 세션 키를 얻음

## 6. 인증서 (certificate)

- 일상에서 말하는 인증서처럼, 무언가가 진짜임을 증명하는 문서
- 인터넷에서 인증서라고 하면 보통 공개 키 인증서를 말함

### 공개 키 인증서가 필요한 이유

- 웹 서버가 내 컴퓨터에 공개 키를 보냈다고 치자
- 그런데 이 공개 키가 진짜 그 서버 것인지, 중간에 누가 바꿔치기한 건 아닌지 알 방법이 없음
- 그래서 서버는 공개 키만 보내지 않고, 인증서에 담아서 보냄

### 공개 키 인증서에 들어 있는 것

- 공개 키 (이건 꼭 기억할 것)
- 누가 만들었는지(발급자)
- 유효 기간
- 서명 값 등

### 인증 기관 (CA, Certification Authority)

- 인증서를 발급하고 검증해 주는 믿을 수 있는 제3의 기관
- 예: IdenTrust, DigiCert, GlobalSign 등
- CA가 발급한 인증서에는 “이 인증서 진짜임, 내가 보증함”이라는 뜻의 서명 값(signature)이 들어 있음
- 클라이언트는 이 서명 값으로 인증서가 진짜인지 확인함

CA가 서명 값을 붙여 서버에 인증서 발급 → 서버가 클라이언트에게 인증서 전달

![CA가 서명 값을 붙여 서버에 인증서 발급 → 서버가 클라이언트에게 인증서 전달](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/f0647ebf-8d41-4fa5-b949-a124baa8b080.png)

CA가 서명 값을 붙여 서버에 인증서 발급 → 서버가 클라이언트에게 인증서 전달

## 7. 서명 값은 어떻게 만드나

1. 인증서 내용을 해시 함수에 넣어 해시 값을 구함
2. 그 해시 값을 CA의 개인 키로 암호화함 → 이게 서명 값
3. CA는 인증서 + 서명 값을 함께 보냄
- 참고: 1번에서 나온 “인증서 내용의 해시 값”을 지문(fingerprint)이라고도 부름

인증서 → 해시 함수 → 해시 값 → CA 개인 키로 암호화 → 인증서와 함께 전송

![인증서 → 해시 함수 → 해시 값 → CA 개인 키로 암호화 → 인증서와 함께 전송](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/ea9bee7c-351b-4508-bb3c-e4175b4252e3.png)

인증서 → 해시 함수 → 해시 값 → CA 개인 키로 암호화 → 인증서와 함께 전송

### 참고: 해시 값이란

- 해시 함수: 길이가 제각각인 데이터를 넣으면 항상 같은 길이의 값으로 바꿔 주는 함수
- 해시 값: 해시 함수를 거쳐 나온 결과
- 대표적인 해시 함수: MD5, SHA-1, SHA-2(SHA-256, SHA-384, SHA-512)
- 특징: 입력이 한 글자만 달라도 결과가 완전히 달라짐
- 그래서 데이터가 중간에 바뀌었는지 확인하는 데 씀
    - 보내는 쪽: 데이터 + 그 데이터의 해시 값을 같이 보냄
    - 받는 쪽: 받은 데이터로 해시 값을 직접 계산해서 받은 해시 값과 비교
    - 같으면 → 중간에 바뀌거나 빠진 게 없다고 판단

## 8. 인증서 검증 과정과 디지털 서명

브라우저가 서버에게서 서명 값이 붙은 인증서를 받았을 때

1. 받은 것을 서명 값과 인증서로 나눔
2. 서명 값을 CA의 공개 키로 복호화 → “인증서 내용의 해시 값”이 나옴
(CA의 공개 키는 공개돼 있으니 누구나 할 수 있음)
3. 받은 인증서 내용으로 해시 값을 직접 계산함
4. 2번과 3번 값을 비교함
- 두 값이 같으면 → 이 서명은 진짜 CA의 개인 키로 만든 것이 확실함
- 따라서 인증서 안의 공개 키도 믿고 써도 됨

① 분리 → ② CA 공개 키로 복호화해 해시 값 얻기 / ③ 인증서를 해시 함수로 계산 → ④ 비교

![① 분리 → ② CA 공개 키로 복호화해 해시 값 얻기 / ③ 인증서를 해시 함수로 계산 → ④ 비교](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/1e3dac7a-7b04-445c-8798-f8bceafb02e7.png)

① 분리 → ② CA 공개 키로 복호화해 해시 값 얻기 / ③ 인증서를 해시 함수로 계산 → ④ 비교

### 디지털 서명 (digital signature)

- 개인 키로 잠근 것을 공개 키로 열어 봄으로써 “누가 보냈는지”를 증명하는 방법
- 앞의 공개 키 암호화와 방향이 반대임
    - 비밀 전달: 공개 키로 잠금 → 개인 키로 엶
    - 신원 증명: 개인 키로 잠금 → 공개 키로 엶

## 9. SSL과 TLS

- 지금까지 배운 대칭 키, 공개 키, 인증서를 바탕으로 동작하는 프로토콜
- 역할: 인증(상대가 진짜인지 확인) + 암호화
- SSL: Secure Sockets Layer
- TLS: Transport Layer Security. SSL을 이어받은 후속 프로토콜
- 버전 흐름: SSL 2.0 → SSL 3.0 → TLS 1.0 → TLS 1.1 → TLS 1.2 → TLS 1.3
(SSL 1.0은 공개되지 않음)
- 버전과 알고리즘에 따라 세부 동작은 조금씩 다르지만 큰 틀은 비슷함

## 10. HTTPS

- HTTP over TLS. HTTP 메시지를 SSL/TLS로 안전하게 주고받는 프로토콜
- 브라우저 주소창 왼쪽의 자물쇠 아이콘 = 그 사이트가 HTTPS를 쓴다는 뜻
- 즉, 사이트와 내 브라우저 사이 통신이 암호화되고 있다는 의미브라우저 주소창 자물쇠 클릭 시 “이 연결은 안전합니다” 표시 화면

![브라우저 주소창 자물쇠 클릭 시 “이 연결은 안전합니다” 표시 화면](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/a015f542-24e9-438d-ae71-a68d91a7a66e.png)

### HTTPS 통신 3단계 (TLS 1.3 기준)

1. TCP 쓰리 웨이 핸드셰이크
2. TLS 핸드셰이크
3. 암호화된 메시지 주고받기

### 1단계: TCP 쓰리 웨이 핸드셰이크

- TCP 연결을 맺는 과정 (4장 내용)
- SYN → SYN+ACK → ACK 순서로 세그먼트를 주고받음

## 11. TLS 핸드셰이크

핵심은 딱 두 가지임

- 암호화에 쓸 키를 주고받음 (키 교환)
- 인증서를 보내고 검증함

메시지 이름을 다 외울 필요는 없음

![TLS 1.3 핸드셰이크 흐름](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/919f1887-dadf-4536-841e-51316cc246d8.png)

### ClientHello (클라이언트 → 서버)

- “이런 방식들 쓸 수 있어, 골라 봐” 하고 제안하는 메시지
- 들어 있는 것
    - 지원하는 TLS 버전
    - 쓸 수 있는 암호화 방식과 해시 함수 목록
    - 키 만들 때 쓸 클라이언트 쪽 난수
- 암호 스위트(cipher suite): 암호화 방식 + 해시 함수를 묶은 조합

![암호 스위트 예시 목록. 가운데가 암호화 알고리즘, 끝이 해시 함수](../../IMG/혼자%20공부하는%20네트워크/PART_07/02/02f13462-4f28-4a84-a4c7-e00aef81772e.png)

### ServerHello (서버 → 클라이언트)

- 클라이언트가 제안한 것 중에서 고른 결과를 알려 주는 메시지
- 들어 있는 것
    - 선택한 TLS 버전
    - 선택한 암호 스위트
    - 키 만들 때 쓸 서버 쪽 난수
- ClientHello와 ServerHello를 주고받으면 암호화 방식이 정해짐
- 정해진 정보로 양쪽이 각자 암호화 키를 만들어 냄 → 이게 TLS 핸드셰이크의 키 교환
- 이후부터는 암호문으로 주고받을 수 있음

### Certificate, CertificateVerify (서버 → 클라이언트)

- Certificate: 서버의 인증서
- CertificateVerify: 검증용 디지털 서명
- 클라이언트는 이걸로 서버의 공개 키가 믿을 만한지 확인함

### Finished (양쪽)

- TLS 핸드셰이크가 끝났다는 신호

## 12. 3단계: 암호화된 데이터 주고받기

- 핸드셰이크로 만든 키로 데이터를 암호화해서 주고받으면 됨
- TLS 1.3에서는 Finished 메시지와 함께 바로 암호화된 데이터(Application Data)를 보낼 수 있음

## 핵심 정리

- 대칭 키 암호화: 암호화와 복호화에 같은 키를 씀
- 공개 키 암호화: 서로 다른 두 키를 씀. 한 키로 잠그면 다른 키로 열 수 있음
- 공개 키 인증서: 공개 키와 그 공개 키가 믿을 만하다는 걸 증명하는 전자 문서. CA를 통해 검증함
- 디지털 서명: 개인 키로 잠근 걸 공개 키로 열어서 보낸 사람의 신원을 증명하는 방법
- SSL/TLS: 인증과 암호화를 해 주는 프로토콜. TLS는 SSL의 후속. 대표적으로 HTTPS에서 씀
- TLS 핸드셰이크: 암호화에 쓸 키와 인증서를 주고받는 과정
