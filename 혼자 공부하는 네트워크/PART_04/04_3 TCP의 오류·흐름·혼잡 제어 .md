# 오류 제어 : 재전송 기법

## 오류 검출과 재전송

TCP 세그먼트에 오류 검출을 위한 체크섬 필드 있음

<aside>

체크섬 필드 : 송신 호스트가 전송 과정에 문제가 있다는 것 인지 X

- 훼션 여부만 나타남
- 값이 잘못됐다면 호스트는 패킷 안 읽고 폐기
</aside>

### TCP가 신뢰성을 제대로 보장하기 위해서

1. 송신 호스트가 송신한 세그먼트에 문제가 발생했을음 인지할 수 있어야
2. 오류를 감지하게 되면 해당 세그먼트를 재전송할 수 있어야

### 1. 송신한 세그먼트에 문제가 있음을 감지하느냐

#### ① 중복된 ACK 세그먼트를 수신했을 때

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%201.png)

수신 호스트 측이 받은 세그먼트의 순서 번호 중에서 일부가 누락되었으면 중복된 세그먼트 전송

#### ② 타임 아웃이 발생했을 때

호스트가 세그먼트 전공할 때마다 **재전송 타이머 (retransmission timer)** 시작하는데, 타이머의 카운트 다운이 끝난 **타임아웃 (timeout)** 이 발생할 때까지 ACK 세그먼트 못받았을 때

## ARQ (Automatic Repeat Request; 자동 재전송 요구)

문제를 진단하고 문제가 생긴 메세지를 재전송하면서 신뢰성 확보하는 방식

### 1. Stop-and-Wait ARQ

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%203.png)

- 제대로 전달했음을 확인하기 전까지 새로운 메세지 보내지 않음
- 단순하지만 높은 신뢰성
- 네트워크 이용 효율이 낮아짐 : 많은 데이터가 있는데 하나씩만 확인해야 하니 성능 저하

⇒ 문제를 해결하기 위해 ACK 세그먼트가 도착하기 전이라도 여러 세그먼트를 보낼 수 있어야 한다

**⇒ 연속해서 메세지를 전송할 수 있는 기술 = 파이프라이닝(pipelining)**

오늘날의 TCP는 파이프라이닝이 사용되는 2번, 3번을 기반으로 동작

### 2. Go-Back-N ARQ

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%204.png)

여러 세그먼트를 전송하지만, 도중에 잘못 전송된 세그먼트가 발생할 경우 **해당 세그먼트부터 전부 다시 전송**

받지 못한 오류 세그먼트  다음 세그먼트는 폐기
→ 오류 세그먼트에 대해서는 타임 아웃이 발생 : 잘못된 송신 인지
→ 오류 세그먼트부터 재전송

순서번호 n번에 대한 ACK 세그먼트는 **n번까지의 확인 응답** = **누적 확인 응답 (CACK; Cumulative Acknowledgment)** 라고도 부름

### 3. Selective Repeat ARQ

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%205.png)

수신 호스트 측에서 제대로 전송받은 각각의 패킷에 대해 ACK 세그먼트 보냄

올바르게 수신받지 못한 ACK 세그먼트 검사하고, 응답받지 못한 세그먼트를 **선택적으로 재전송** = **개별 확인 응답 (Selective Acknowledgment)**

# 흐름 제어 : 슬라이딩 윈도우

한 번에 받아서 처리할 수 있는 세그먼트 양에는 **한계**가 있기 때문에 파이프라이닝 기반의 ARQ가 정상적으로 동작하려면 **흐름 제어 (Flow control)** 가 중요

송신 호스트가 *수신 버퍼보다 많은 데이터를 전송하면 일부 세그먼트 처리 X

*수신 버퍼 : 수신 세그먼트가 어플리케이션 프로세스에 의해 읽히기 전에 임시로 저장되는 공간

*버퍼 오버플로 (Buffer overflow) : 버퍼가 넘치는 문제 상황

⇒ TCP 의 흐름 제어 = 송신 호스트가 수신 호스트의 처리 속도를 고려하며 송수신 속도를 균일하게 유지하는것

## 슬라이딩 윈도우 Sliding Window

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%206.png)

윈도우 : 송신 호스트가 파이프라이닝할 수 있는 최대량. 

TCP 세그먼트 내의 윈도우 필드에서 수신 윈도우의 크기 명시

- 수신 호스트는 TCP 헤더를 통해 송신 호스트에게 받아들일 수 있는 데이터 양 알려줌
- 송신 호스트는 정보를 바탕으로 수신 호스트의 처리 속도 맞춰 전송

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%207.png)

파이프라이닝 과정에서 윈도우를 오른쪽으로 미끄러지듯 움직여서 전송

# 혼잡 제어 (Congestion Control)

혼잡 (Congestion) : 많은 트래픽으로 패킷 처리 속도가 늦거나 유실되는 상황

TCP의 혼잡 제어 : 혼잡 윈도우 (Congestion Window)로 관리

송신 호스트 : 혼잡도 판단하고 정도에 맞춰 유동적으로 전송량 조절하며 전송

혼잡 위도우 : 혼잡 없이 전송할 수 있을 법한 데이터의 양

## 혼잡 윈도우의 크기

송신 호스트가 혼잡을 방지할 수 있는지 직접 계산해서 확인 = 혼잡 제어를 수행하는 방법 혼잡 제어 알고리즘 (Congestion Control Algorithm)

### AIMD; Additive Increase/Multiplicative Decrease 알고리즘

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%208.png)

혼잡이 감지되지 않는다면 RTT(Round Trip Time)마다 1씩 선형적으로 증가,

감지되지 않는다면 절반으로 떨어트리기

느린 시작 임계치 (Slow Start Threshold) 값도 같이 사용

#### ① 느린 시작 알고리즘 (Slow Start)

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%209.png)

혼잡 윈도우를 1부터 시작해 수신된 ACK 세그먼트 당 1씩 증가

| 상황 분류 | 방법 |
| --- | --- |
| 타임아웃 발생 |   • 혼잡 윈도우 값 = 1 </br> • 느린 시작 임계치 초기화 = 혼잡이 감지되었을 시점의 혼잡 윈도우 값의 절반 </br> • 느린 시작 재개 |
| 혼잡 윈도우 ≥ 느린 시작 임계치 |   • 느린 시작 종료 </br> • 혼잡 윈도우 초기화 = 절반 </br> • 혼잡 회피 수행 |
| 세 번의 중복 ACK |   • 빠른 재전송 후 빠른 회복 수행 |

#### ② 혼잡 회피(Congestion Avoidance) 알고리즘

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/3/image%2010.png)

RTT마다 혼잡 윈도우를 **1MSS (Maximum Segment Size)** 씩 증가

지수적으로 증가시키는 느린 시작과 달리 선형적으로 증가

#### ③ 빠른 회복 (Fast Recovery) 알고리즘

세 번의 중복된 ACK 세그먼트를 수신했을 때 수행

느린 시작은 건너 뛰고 혼잡 회피를 수행하는 알고리즘
