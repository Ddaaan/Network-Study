## tcp와 udp

### TCP vs. UDP

- TCP : 신뢰할 수 있는 통신을 위한 연결형 프로토콜
- UDP : 신뢰성은 떨어지지만 빠른 통신이 가능한 비연결형 프로토콜

### TCP 통신 단계와 세그먼트 구조

아래 그림은 TCP 통신을 크게 3가지로 나눈 것

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/2/1.png)

- TCP는 통신하기 전에 연결을 수립하고 통신이 끝나면 연결을 종료
- 데이터 송수신 과정에서 재전송을 통한 오류 제어, 흐름 제어, 혼잡 제어 등의 기능을 제공

#### MSS (Maximum Segment Size)

- TCP로 전송할 수 있는 최대 페이로드 크기
- 크기를 고려할 때 TCP 헤더 크기는 제외 (MTU는 헤더의 크기까지 포함했었음)

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/2/2.png)

#### TCP 세그먼트 구조

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/2/3.png)

- **송신지 포트와 수신지 포트**  
  송신지 또는 수신지 애플리케이션을 식별하는 포트 번호가 명시되는 필드

- **순서 번호**  
  순서 번호란 송수신되는 세그먼트의 올바른 순서를 보장하기 위해 세그먼트 데이터의 첫 바이트에 부여되는 번호

- **확인 응답 번호**  
  상대 호스트가 보낸 세그먼트에 대한 응답, 다음으로 수신하기를 기대하는 순서 번호가 명시됨

- **제어 비트**  
  flag bits라고도 부름. 현재 세그먼트에 대한 부가 정보를 나타냄

- **윈도우**  
  수신 윈도우의 크기가 명시됨. 수신 윈도우란 한 번에 수신하고자 하는 데이터의 양을 나타냄

#### 제어 비트

기본적으로 8비트로 구성, 각 자리 비트는 각기 다른 의미를 가짐

- **ACK**: 세그먼트의 승인을 나타내기 위한 비트
- **SYN**: 연결을 수립하기 위한 비트
- **FIN**: 연결을 종료하기 위한 비트

#### 순서 번호와 확인 응답 번호

TCP의 신뢰성을 보장하기 위해 사용되는 중요한 필드, 한 쌍으로 묶어서 기억하기!

##### 확인 응답 번호

확인 응답 번호는 순서 번호에 대한 응답으로, **수신자가 다음으로 받기를 기대하는 순서 번호**를 의미함  
즉, 송신자에게 "여기까지 잘 받았고, 다음에는 이 순서 번호부터 보내 주세요"라고 알려 주는 값

- 일반적으로 `수신한 마지막 바이트의 순서 번호 + 1`로 설정
- 확인 응답 번호를 전송할 때는 제어 비트의 **ACK 플래그를 1**로 설정

**<예시>**

호스트 A가 순서 번호가 `8000`인 세그먼트를 호스트 B에게 전송했고, 호스트 B가 이를 정상적으로 수신한 경우

1. 호스트 B는 다음 순서 번호인 `8001`을 받기를 기대함
2. ACK 플래그를 `1`로 설정함
3. 확인 응답 번호를 `8001`로 설정한 세그먼트를 호스트 A에게 전송함

따라서 확인 응답 번호를 통해 상대 호스트가 데이터를 어디까지 정상적으로 수신했는지 알 수 있음

### TCP 연결 수립과 종료

#### 연결 수립 : 3-way handshake

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/2/8.png)

TCP는 통신을 시작하기 전에 **3-way handshake**를 통해 연결을 수립함

| 순서 | 송수신 방향 | 세그먼트 | 세그먼트에 포함된 주요 정보 |
| --- | --- | --- | --- |
| 1 | A → B | SYN 세그먼트 | 호스트 A의 초기 순서 번호, `1`로 설정된 SYN 비트 |
| 2 | B → A | SYN + ACK 세그먼트 | 호스트 B의 초기 순서 번호, 호스트 A가 전송한 세그먼트에 대한 확인 응답 번호, `1`로 설정된 SYN 비트와 ACK 비트 |
| 3 | A → B | ACK 세그먼트 | 호스트 A의 다음 순서 번호, 호스트 B가 전송한 세그먼트에 대한 확인 응답 번호, `1`로 설정된 ACK 비트 |

1. 호스트 A가 호스트 B에게 **SYN 세그먼트**를 전송하여 연결 수립을 요청함
2. 호스트 B가 **SYN + ACK 세그먼트**를 전송하여 요청을 확인하고 연결 수립을 요청함
3. 호스트 A가 **ACK 세그먼트**를 전송하여 호스트 B의 요청을 확인함

- **액티브 오픈(active open)**: 먼저 연결을 시작하는 호스트의 연결 수립 과정
  - 연결을 처음 요청하는 측의 동작
  - 주로 서버-클라이언트 관계에서 클라이언트가 수행
  - 위 예시에서는 호스트 A의 동작
- **패시브 오픈(passive open)**: 연결 요청을 받은 뒤 요청에 따라 연결을 수립하는 호스트의 연결 수립 과정
  - 주로 서버가 수행
  - 위 예시에서는 호스트 B의 동작

#### 연결 종료

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/2/9.png)

데이터 송수신이 끝나면 송수신 호스트가 각자 한 번씩 FIN과 ACK를 주고받으며 연결을 종료함

| 순서 | 송수신 방향 | 세그먼트 | 세그먼트에 포함된 주요 정보 |
| --- | --- | --- | --- |
| 1 | A → B | FIN 세그먼트 | `1`로 설정된 FIN 비트 |
| 2 | B → A | ACK 세그먼트 | 호스트 A가 전송한 세그먼트에 대한 확인 응답 번호, `1`로 설정된 ACK 비트 |
| 3 | B → A | FIN 세그먼트 | `1`로 설정된 FIN 비트 |
| 4 | A → B | ACK 세그먼트 | 호스트 B가 전송한 세그먼트에 대한 확인 응답 번호, `1`로 설정된 ACK 비트 |

1. 호스트 A가 호스트 B에게 **FIN 세그먼트**를 전송하여 연결 종료를 요청함
2. 호스트 B가 **ACK 세그먼트**를 전송하여 요청을 확인함
3. 호스트 B도 **FIN 세그먼트**를 전송하여 연결 종료를 요청함
4. 호스트 A가 **ACK 세그먼트**를 전송하여 요청을 확인함

> 네 단계로 연결을 종료한다는 점에서 **4-way handshake**라고 부르기도 함

- **액티브 클로즈(active close)**: 먼저 연결을 종료하려는 호스트가 수행
  - 위 예시에서는 FIN 세그먼트를 먼저 보낸 호스트 A의 동작
- **패시브 클로즈(passive close)**: 연결 종료 요청을 받아들이는 호스트가 수행
  - 위 예시에서는 호스트 B의 동작

### TCP 상태

TCP는 연결형 통신과 신뢰할 수 있는 통신을 유지하기 위해 현재 통신 과정을 나타내는 다양한 **상태(state)**를 유지함  
이처럼 상태를 유지하고 활용하는 프로토콜을 **스테이트풀(stateful) 프로토콜**이라고 함

TCP 상태는 크게 다음과 같이 구분할 수 있음

| 구분 | 주요 상태 |
| --- | --- |
| 연결이 수립되지 않은 상태 | CLOSED, LISTEN |
| 연결 수립 과정의 상태 | SYN-SENT, SYN-RECEIVED, ESTABLISHED |
| 연결 종료 과정의 상태 | FIN-WAIT-1, CLOSE-WAIT, FIN-WAIT-2, LAST-ACK, TIME-WAIT, CLOSING, CLOSED |

#### 연결이 수립되지 않은 상태

- **CLOSED**: 아무런 연결이 없는 상태
- **LISTEN**: 연결 요청을 기다리는 상태
  - 일반적으로 패시브 오픈을 수행하는 서버가 유지함
  - LISTEN 상태의 호스트가 SYN 세그먼트를 받으면 3-way handshake가 시작됨

#### 연결 수립 상태

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/2/10.png)

- **SYN-SENT**
  - 액티브 오픈 호스트가 SYN 세그먼트를 전송한 뒤 SYN + ACK 세그먼트를 기다리는 상태
- **SYN-RECEIVED**
  - 패시브 오픈 호스트가 SYN + ACK 세그먼트를 전송한 뒤 ACK 세그먼트를 기다리는 상태
- **ESTABLISHED**
  - 연결이 확립되어 데이터를 송수신할 수 있는 상태
  - 3-way handshake의 마지막 ACK 세그먼트를 주고받으면 두 호스트 모두 이 상태가 됨

**3-way handshake의 상태 변화**

1. 액티브 오픈 호스트: `CLOSED → SYN-SENT → ESTABLISHED`
2. 패시브 오픈 호스트: `LISTEN → SYN-RECEIVED → ESTABLISHED`

#### 연결 종료 상태

![image.png](../../IMG/혼자%20공부하는%20네트워크/PART_04/2/11.png)

- **FIN-WAIT-1**
  - 액티브 클로즈 호스트가 FIN 세그먼트를 전송한 뒤 응답을 기다리는 상태
- **CLOSE-WAIT**
  - 패시브 클로즈 호스트가 FIN 세그먼트를 받고 ACK 세그먼트를 전송한 뒤 대기하는 상태
- **FIN-WAIT-2**
  - 액티브 클로즈 호스트가 자신의 FIN에 대한 ACK를 받고 상대 호스트의 FIN을 기다리는 상태
- **LAST-ACK**
  - 패시브 클로즈 호스트가 FIN 세그먼트를 전송한 뒤 마지막 ACK를 기다리는 상태
- **TIME-WAIT**
  - 액티브 클로즈 호스트가 상대의 FIN을 받고 마지막 ACK를 전송한 뒤 일정 시간 대기하는 상태
  - 대기 시간이 지나면 CLOSED 상태로 전이함
- **CLOSING**
  - 양쪽 호스트가 거의 동시에 FIN 세그먼트를 보내 연결 종료를 요청한 경우의 상태
  - 자신의 FIN에 대한 ACK를 받으면 TIME-WAIT 상태로 전이함
- **CLOSED**
  - 연결이 완전히 종료된 상태

**일반적인 4-way handshake의 상태 변화**

1. 액티브 클로즈 호스트: `ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED`
2. 패시브 클로즈 호스트: `ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED`

##### TIME-WAIT 상태가 필요한 이유

- 마지막 ACK 세그먼트가 상대 호스트에게 정상적으로 전달되지 않을 수 있기 때문
  - 상대 호스트가 FIN을 재전송하면 마지막 ACK를 다시 전송할 수 있음
- 이전 연결의 패킷과 새 연결의 패킷이 뒤섞이는 것을 방지하기 위함

### UDP 데이터그램 구조

UDP는 비연결형 통신을 수행하는 **신뢰할 수 없는 프로토콜**임

- 연결 수립과 연결 종료 과정을 거치지 않음
- 재전송을 통한 오류 제어, 흐름 제어, 혼잡 제어를 수행하지 않음
- TCP처럼 상태를 유지하지 않으므로 **스테이트리스(stateless) 프로토콜**이라고 함

UDP는 TCP보다 제공하는 기능이 적은 만큼 헤더 구조가 단순함

UDP 헤더는 다음과 같은 네 개의 필드로 구성되며, 각 필드의 크기는 16비트임

| 필드 | 설명 |
| --- | --- |
| 송신지 포트 | 송신지의 포트 번호 |
| 수신지 포트 | 수신지의 포트 번호 |
| 길이 | 헤더를 포함한 UDP 데이터그램의 전체 바이트 수 |
| 체크섬 | 데이터그램 전송 과정에서 오류가 발생했는지 검사하기 위한 값 |

체크섬 값을 토대로 데이터그램이 훼손되었다고 판단되면 해당 데이터그램을 폐기함  
체크섬은 데이터그램의 훼손 여부만 확인하므로 수신지까지 잘 전달되었는지를 보장하는 신뢰성과는 관련이 없음

#### UDP의 특징

- TCP보다 오버헤드가 적어 패킷을 빠르게 처리할 수 있음
- 패킷의 전달 여부나 순서를 보장하지 않음
- 전송 과정에서 패킷이 손실되거나 순서가 바뀔 수 있음
- 실시간 스트리밍 서비스나 인터넷 전화처럼 실시간성이 중요한 상황에서 주로 사용됨
