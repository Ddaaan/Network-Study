# HTTP 메서드

HTTP 메서드는 클라이언트가 서버에게 **자원에 대해 무엇을 해 달라고 요청하는지** 알려 주는 명령어

예를 들어 같은 `/posts/1`이라는 주소를 사용하더라도 메서드에 따라 요청의 의미가 달라짐

- `GET /posts/1` → 1번 게시글 조회
- `PATCH /posts/1` → 1번 게시글 일부 수정
- `DELETE /posts/1` → 1번 게시글 삭제

## HTTP 메서드 한눈에 보기

| 메서드 | 쉬운 의미 | 주요 용도 |
| --- | --- | --- |
| `GET` | 가져오기 | 자원 조회 |
| `HEAD` | 헤더만 가져오기 | 자원의 헤더 정보만 조회 |
| `POST` | 작업 처리 | 데이터 전송, 새 자원 생성 |
| `PUT` | 전체 변경 | 기존 자원 전체 교체 |
| `PATCH` | 일부 변경 | 기존 자원 일부 수정 |
| `DELETE` | 삭제 | 자원 삭제 |
| `CONNECT` | 연결 통로 생성 | 서버와 양방향 터널 연결 시작 |
| `OPTIONS` | 사용 가능 기능 확인 | 서버가 지원하는 통신 옵션 확인 |
| `TRACE` | 요청 경로 확인 | 요청 경로의 루프백 테스트 |

> 자주 사용하는 대표적인 메서드는 `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`임.

---

## GET - 자원 가져오기

`GET`은 서버에 있는 **자원을 조회**할 때 사용하는 메서드임. 웹 브라우저로 웹 페이지를 열거나 게시글 목록을 확인하는 동작이 대표적!!!

### 요청 예시

```http
GET /example-page HTTP/1.1
Host: www.example.com
Accept: *
```

- `GET` : 자원을 조회하겠다는 뜻
- `/example-page` : 가져올 자원의 경로
- `HTTP/1.1` : 사용할 HTTP 버전
- `Host` : 요청을 받을 서버
- `Accept` : 클라이언트가 받을 수 있는 데이터 형식

### 응답 예시

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<!DOCTYPE html>
<html>
  <body>
    <h1>Hello, World!</h1>
  </body>
</html>
```

요청이 성공하면 서버는 `200 OK`와 함께 요청한 자원을 응답 본문에 담아 보냄

### 쿼리 문자열로 조건 전달하기

`GET`은 보통 요청 본문 대신 URL 뒤의 **쿼리 문자열**로 조건을 전달

```http
GET /index.html?name1=value1&name2=value2 HTTP/1.1
Host: www.example.com
Accept: *
```

- `?` 뒤에 `이름=값` 형태로 조건 작성
- 조건이 여러 개라면 `&`로 구분

> `GET` 요청에 본문을 넣는 것이 문법적으로 완전히 금지된 것은 아니지만, 일반적으로 권장하지 않으며 서버가 이를 무시할 수도 있음.

## HEAD - 헤더만 가져오기

`HEAD`는 `GET`과 거의 같지만, 서버가 **응답 본문을 보내지 않고 헤더만 반환**함.

파일을 실제로 내려받지 않고도 파일의 크기, 형식, 수정 여부 등을 확인할 때 유용함.

### 요청 예시

```http
HEAD /example-page HTTP/1.1
Host: www.example.com
Accept: *
```

### 응답 예시

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234
```

`Content-Length`는 있지만 실제 HTML 문서는 응답 본문에 포함되지 않음.

---

## POST - 작업 처리

`POST`는 클라이언트가 데이터를 보내면서 서버에 **특정 작업을 처리해 달라고 요청**할 때 사용함.

활용 범위가 넓으며 주로 다음과 같은 상황에서 사용함.

- 새 게시글이나 회원 정보 등록
- 로그인 정보 제출
- 주문 생성
- 서버에서 정해 둔 작업 실행

### 요청 예시

```http
POST /posting HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "title": "오늘도 즐거운 날입니다",
  "contents": "재미있는 글 보고 가세요~"
}
```

처리할 데이터는 주로 요청 본문에 담김. 위 요청은 서버에 게시글을 새로 만들어 달라는 의미임.

### 응답 예시

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /posting/1

{
  "id": 1,
  "title": "오늘도 즐거운 날입니다",
  "contents": "재미있는 글 보고 가세요~"
}
```

- `201 Created` : 새 자원이 성공적으로 생성됨
- `Location: /posting/1` : 새로 생성된 자원의 위치

> `POST`가 항상 새 자원을 만드는 것은 아님. 최종 동작은 서버가 API를 어떻게 설계했는지에 따라 달라짐.

---

## PUT - 전체 교체

`PUT`은 특정 위치의 자원을 요청 본문의 내용으로 **완전히 교체**할 때 사용함. 쉽게 말해 기존 내용을 새 내용으로 덮어쓰는 것과 비슷함.

기존 자원이 다음과 같다고 가정.

```json
{
  "id": 1,
  "title": "오늘도 즐거운 날입니다",
  "contents": "재미있는 글 보고 가세요~"
}
```

다음과 같이 `PUT` 요청을 보냄.

```http
PUT /posting/1 HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "id": 1,
  "title": "수정된 제목입니다"
}
```

서버가 이를 전체 교체로 처리하면 결과는 다음처럼 될 수 있음.

```json
{
  "id": 1,
  "title": "수정된 제목입니다"
}
```

요청 본문에 없던 `contents`가 사라질 수 있다는 점에 주의 필요

> `PUT`의 세부 처리 방식은 API 설계에 따라 다를 수 있으므로 해당 API 문서 확인 필요

---

## PATCH - 일부 수정

`PATCH`는 기존 자원에서 **원하는 부분만 수정**할 때 사용함.

```http
PATCH /posting/1 HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "title": "수정된 제목입니다"
}
```

위 요청은 `title`만 수정하므로 기존의 `contents`는 그대로 남음.

```json
{
  "id": 1,
  "title": "수정된 제목입니다",
  "contents": "재미있는 글 보고 가세요~"
}
```

### PUT과 PATCH의 차이

| 구분 | `PUT` | `PATCH` |
| --- | --- | --- |
| 쉬운 표현 | 전부 바꿔 주세요 | 일부만 바꿔 주세요 |
| 수정 범위 | 자원 전체 | 자원의 일부 |
| 요청에 없는 필드 | 사라질 수 있음 | 일반적으로 유지됨 |

---

## DELETE - 자원 삭제

`DELETE`는 서버의 특정 자원을 **삭제**할 때 사용하는 메서드임.

```http
DELETE /texts/a.txt HTTP/1.1
Host: example.com
```

위 요청은 `example.com` 서버에 있는 `/texts/a.txt` 자원을 삭제해 달라는 의미임.

삭제가 성공하면 서버는 상황에 따라 `200 OK` 또는 응답 본문이 없는 `204 No Content` 등을 반환할 수 있음.

---

## 같은 URL도 메서드에 따라 의미가 달라진다

서버는 **URL과 HTTP 메서드를 함께 보고** 어떤 동작을 수행할지 결정함.

| 요청 | 의미 |
| --- | --- |
| `GET /posting/1` | 1번 게시글을 조회한다. |
| `POST /posting` | 새 게시글을 등록한다. |
| `PUT /posting/1` | 1번 게시글 전체를 교체한다. |
| `PATCH /posting/1` | 1번 게시글 일부를 수정한다. |
| `DELETE /posting/1` | 1번 게시글을 삭제한다. |

어떤 URL에서 어떤 메서드를 허용할지, 요청에 어떤 값을 담을지, 성공·실패 시 어떤 응답을 줄지는 서버 개발자가 정함.

## API 문서란?

**API 문서**는 클라이언트가 서버를 올바르게 사용할 수 있도록 약속을 정리한 설명서임.

보통 다음 내용 확인 가능.

- 요청을 보낼 URL
- 사용할 HTTP 메서드
- 전달할 경로 변수, 쿼리 문자열, 요청 본문
- 필요한 요청 헤더와 인증 방법
- 성공했을 때 받을 상태 코드와 응답 데이터
- 잘못 요청했을 때 받을 오류 코드와 오류 메시지

따라서 API를 사용할 때는 메서드 이름만 보고 동작을 단정하지 않고, **해당 서비스의 API 문서를 먼저 확인하는 습관**이 중요함.

# HTTP 상태 코드

HTTP 상태 코드는 서버가 클라이언트의 요청을 처리한 결과를 알려 주는 **세 자리 숫자**임.

백의 자리 숫자를 보면 결과의 큰 범주를 빠르게 파악할 수 있음.

| 범위 | 쉬운 의미 | 설명 |
| --- | --- | --- |
| `100~199` | 요청을 처리하고 있어요 | 정보성 상태 코드 |
| `200~299` | 요청에 성공했어요 | 성공 상태 코드 |
| `300~399` | 다른 곳으로 가세요 | 리다이렉션 상태 코드 |
| `400~499` | 요청에 문제가 있어요 | 클라이언트 오류 상태 코드 |
| `500~599` | 서버에 문제가 있어요 | 서버 오류 상태 코드 |

> 상태 코드의 의미를 모두 외우기보다는 먼저 `2xx는 성공`, `4xx는 요청 문제`, `5xx는 서버 문제`처럼 범주를 이해하는 것이 좋음.

## 200번대 - 요청 성공

200번대 상태 코드는 요청을 정상적으로 받았거나 처리했음을 뜻함.

| 상태 코드 | 이름 | 쉬운 의미 |
| --- | --- | --- |
| `200` | OK | 요청을 성공적으로 처리함 |
| `201` | Created | 요청을 처리하여 새 자원을 생성함 |
| `202` | Accepted | 요청을 접수했지만 처리는 아직 끝나지 않음 |
| `204` | No Content | 처리는 성공했지만 응답 본문은 없음 |

### 200 OK - 정상 처리

가장 일반적인 성공 응답임. 예를 들어 `GET`으로 이미지나 게시글을 요청했고 서버가 해당 자원을 정상적으로 보내 주었다면 `200 OK`를 반환할 수 있음.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 1,
  "title": "첫 번째 게시글"
}
```

### 201 Created - 새 자원 생성

`POST` 요청 등으로 새 자원이 만들어졌을 때 사용함. 서버는 `Location` 헤더로 생성된 자원의 위치를 알려 줄 수 있음.

```http
HTTP/1.1 201 Created
Location: /api/resources/123
Content-Type: application/json

{
  "id": 123,
  "name": "New Resource"
}
```

### 202 Accepted - 요청 접수 후 처리 중

요청은 잘 받았지만 작업이 아직 끝나지 않았음을 뜻함. 대용량 파일 처리나 시간이 오래 걸리는 배치 작업처럼 결과를 바로 만들기 어려울 때 사용 가능.

### 204 No Content - 성공했지만 응답 본문 없음

요청을 성공적으로 처리했지만 응답 본문으로 보낼 내용이 없을 때 사용함. 자원을 삭제한 뒤 다음과 같이 응답 가능.

```http
HTTP/1.1 204 No Content
```

## 300번대 - 다른 위치로 이동

300번대 상태 코드는 요청한 자원이 다른 위치에 있어 **추가 요청이 필요함**을 알려 줌. 이를 **리다이렉션**이라고 함.

서버는 보통 `Location` 헤더에 이동할 새 URL을 담아 응답함.

```http
HTTP/1.1 301 Moved Permanently
Location: /new
```

클라이언트는 위 응답을 받으면 `/new`로 다시 요청함.

![301 리다이렉션 요청과 응답 흐름](../../IMG/혼자%20공부하는%20네트워크/PART_05/02/02_01.png)

### 영구적 리다이렉션 - 새 주소를 계속 사용

자원의 주소가 계속 유지될 새 위치로 바뀌었을 때 사용함.

| 상태 코드 | 이름 | 다시 요청할 때 메서드 |
| --- | --- | --- |
| `301` | Moved Permanently | 기존 메서드가 `GET`으로 바뀔 수 있음 |
| `308` | Permanent Redirect | 기존 메서드를 그대로 유지함 |

예를 들어 처음에 `POST` 요청을 보냈다면 다음 요청은 아래처럼 달라질 수 있음.

- `301` 응답 → 클라이언트에 따라 `GET`으로 바뀔 수 있음
- `308` 응답 → `POST`를 그대로 유지함

### 일시적 리다이렉션 - 임시 주소 사용

자원의 위치가 잠시 바뀌었거나 임시 URL을 사용해야 할 때 사용함. 원래 URL은 이후에도 기억해야 함.

| 상태 코드 | 이름 | 다시 요청할 때 메서드 |
| --- | --- | --- |
| `302` | Found | 기존 메서드가 `GET`으로 바뀔 수 있음 |
| `303` | See Other | `GET`으로 변경함 |
| `307` | Temporary Redirect | 기존 메서드를 그대로 유지함 |

### 리다이렉션 코드 한눈에 구분하기

| 구분 | 영구적 | 일시적 |
| --- | --- | --- |
| 메서드가 바뀔 수 있음 | `301` | `302` |
| `GET`으로 변경 | - | `303` |
| 메서드 유지 | `308` | `307` |

> 핵심은 `307`과 `308`이 기존 요청 메서드를 보존한다는 점임.

## 400번대 - 클라이언트 요청 문제

400번대 상태 코드는 클라이언트가 보낸 요청에 문제가 있어 서버가 처리할 수 없음을 뜻함.

| 상태 코드 | 이름 | 쉬운 의미 |
| --- | --- | --- |
| `400` | Bad Request | 요청 내용이나 형식이 잘못됨 |
| `401` | Unauthorized | 유효한 인증 정보가 필요함 |
| `403` | Forbidden | 인증 여부와 관계없이 접근 권한이 부족함 |
| `404` | Not Found | 요청한 자원을 찾을 수 없음 |
| `405` | Method Not Allowed | 해당 URL이 요청 메서드를 지원하지 않음 |

### 400 Bad Request - 잘못된 요청

요청 메시지의 내용이나 형식이 잘못되어 서버가 이해하거나 처리하지 못하는 경우임.

대표적인 예시는 다음과 같음.

- JSON 문법이 잘못됨
- 필수 입력값이 빠짐
- 숫자가 필요한 곳에 문자열을 보냄

### 401 Unauthorized - 인증 필요

요청한 자원에 접근하려면 로그인이 필요하거나, 보낸 인증 정보가 유효하지 않을 때 사용함.

서버는 `WWW-Authenticate` 헤더로 필요한 인증 방법을 알려 줄 수 있음.

> 이름은 `Unauthorized`이지만 실제 의미는 **인증되지 않음**에 가까움.

### 403 Forbidden - 접근 권한 없음

사용자가 누구인지는 확인했지만 해당 작업을 수행할 권한이 없을 때 사용함. 예를 들어 일반 사용자가 관리자 전용 페이지에 접근하는 경우임.

#### 인증과 권한 부여의 차이

| 구분 | 질문 | 예시 |
| --- | --- | --- |
| 인증(Authentication) | 누구인가? | 로그인으로 사용자 확인 |
| 권한 부여(Authorization) | 무엇을 할 수 있는가? | 관리자만 게시글 삭제 가능 |

쉽게 기억하면 다음과 같음.

- `401` → 로그인 정보가 필요하거나 잘못됨
- `403` → 로그인했더라도 권한이 없음

### 404 Not Found - 자원 없음

요청한 URL에 자원이 존재하지 않을 때 사용함. 서버는 보안상의 이유로 존재하지만 공개할 수 없는 자원에도 `404`를 응답할 수 있음.

### 405 Method Not Allowed - 지원하지 않는 메서드

URL은 존재하지만 요청에 사용한 HTTP 메서드를 서버가 지원하지 않을 때 사용함.

예를 들어 조회만 가능한 주소에 `PATCH` 요청을 보내면 `405 Method Not Allowed`를 받을 수 있음.

## 500번대 - 서버 문제

500번대 상태 코드는 요청 자체는 올바르더라도 서버 쪽 문제로 처리하지 못했음을 뜻함.

| 상태 코드 | 이름 | 쉬운 의미 |
| --- | --- | --- |
| `500` | Internal Server Error | 서버 내부에서 예상하지 못한 오류가 발생함 |
| `502` | Bad Gateway | 중간 서버가 뒤쪽 서버에서 잘못된 응답을 받음 |
| `503` | Service Unavailable | 서버를 현재 일시적으로 이용할 수 없음 |

### 500 Internal Server Error - 서버 내부 오류

서버 프로그램의 예외나 설정 문제 등으로 요청을 처리하지 못했을 때 사용하는 일반적인 서버 오류임.

### 502 Bad Gateway - 중간 서버 통신 오류

클라이언트와 최종 서버 사이에는 게이트웨이, 프록시 같은 여러 중간 서버가 존재할 수 있음. 이 중간 서버가 뒤쪽 서버로부터 잘못된 응답을 받으면 `502 Bad Gateway`를 반환할 수 있음.

### 503 Service Unavailable - 일시적으로 이용 불가

서버가 과부하 상태이거나 점검 중이어서 현재 요청을 처리할 수 없을 때 사용함. 잠시 뒤 다시 요청하면 정상적으로 처리될 수도 있음.

## 상태 코드 빠르게 판단하기

1. 백의 자리부터 확인
2. `2xx`이면 성공 여부와 응답 본문 유무 확인
3. `3xx`이면 `Location` 헤더와 메서드 유지 여부 확인
4. `4xx`이면 URL, 요청 형식, 인증 정보와 권한 확인
5. `5xx`이면 서버 프로그램, 중간 서버, 과부하 여부 확인
